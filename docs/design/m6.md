# M6 design — release plumbing + 0.1.0

Status: **implemented (M6.a + M6.b + M6.c).** First tagged release of
Ontos.

## Goal

Turn Ontos from "usable if you clone the repo" into "installable
from PyPI with a matching container on GHCR." Also give the project
a proper release story (CHANGELOG, SemVer, runbook) so contributors
know how to cut the next release.

## SemVer + versioning (M6.a)

Single source of truth is `ontos/_version.py`. `pyproject.toml`
declares `dynamic = ["version"]` and hatchling reads that file at
build time. `ontos.__version__` re-exports it. The Helm chart's
`appVersion` is bumped manually in the release PR to match — I
considered making the chart read from `_version.py` too, but the
chart lives in the same repo and gets bumped in the same PR, so the
duplication is fine and avoids a fragile file-slurping shim.

**Pre-1.0 posture.** Minor bumps MAY include small breaking changes
if they're worth calling out. RELEASING.md pins the specific
reserved reasons for a MAJOR bump before 1.0 (changing the
Article-12 enum values, changing `Fact` on-disk shape, changing the
`Plan` schema in a way that invalidates persisted plans). These are
the load-bearing invariants; anything else can slip.

## Release workflow (M6.b)

`.github/workflows/release.yml`. Triggers on `v*` tag push. Four
jobs:

1. **build** — extracts the version from the tag, verifies it
   matches `ontos/_version.py` (hard fail on mismatch so a tag
   can't ship out of sync with the source), runs `uv build`,
   uploads the sdist + wheel.
2. **publish-pypi** — publishes to PyPI via **OIDC trusted
   publishing**. No API token in the repo — one-time setup at
   pypi.org points the trust anchor at this repo + workflow +
   `pypi` environment. Environment gates the job so a rogue push
   to a fork can't ship.
3. **publish-ghcr** — builds `deploy/Dockerfile`, tags as
   `ghcr.io/enclave-labs-inc/ontos:X.Y.Z` and `:latest`, pushes
   using the auto-provided `GITHUB_TOKEN`. Zero secret setup.
4. **gh-release** — extracts the `[X.Y.Z]` section from
   `CHANGELOG.md` as release notes; attaches the sdist + wheel;
   publishes.

**`workflow_dispatch` with dry_run.** Operators can validate the
workflow without publishing. Default is `dry_run=true` so pressing
the button by mistake doesn't ship anything.

**Concurrency.** Scoped per-tag with `cancel-in-progress=false` —
we never interrupt a release that's already partway through
publishing.

## First release (M6.c)

0.1.0 encompasses M0 through M5 — the full milestone plan from
`docs/design/m1.md` through `docs/design/m5.md`. The CHANGELOG entry
summarizes each milestone under Added and calls out the known
caveats (OpenAIBackend is bridge only; Slack is a placeholder; ER
cascade ships Rules tier only; no Prometheus/OTel yet).

`tests/unit/test_smoke.py::test_package_imports` used to hardcode
`ontos.__version__ == "0.0.1"` — that would rot every release.
Rewrote to check the SemVer shape via regex so bumps don't touch
tests.

## RELEASING.md

Operator runbook. Covers one-time PyPI/GHCR setup, the step-by-step
release process, the dry-run pattern, and the yank/roll-back policy
(never delete a tag after consumers might have pulled; forward-fix
with a patch release; yank the broken version on PyPI but keep the
record).

## What we deliberately NOT doing in M6

- **Signed wheels / signed containers.** PyPI's own file-hash
  integrity is what consumers rely on today; sigstore / cosign is a
  follow-up when a regulated customer asks. Doing it speculatively
  adds moving parts (key management, verifier tooling) that don't
  earn their keep without a named use case.
- **Automated version bump PRs.** Something like release-please
  would autopush a bump PR based on conventional commits — nice, but
  we don't enforce conventional commits and the manual bump takes
  five minutes.
- **Multi-platform image builds (arm64).** Single amd64 image at
  0.1.0. Adding a buildx multi-arch step is trivial; hasn't come up.
- **Prometheus / OTel / mkdocs site.** Was on the option-C menu;
  M6 keeps to the release-plumbing subset because that's the actual
  adoption unblock. Observability + docs site are a separate
  follow-up.

## Roadmap tie-ins

- **First actual release.** Post-merge: tag `v0.1.0` and push.
  Workflow ships everything. RELEASING.md walks through it.
- **Vertical launch package (option B from the "what next?" menu).**
  Once 0.1.0 is on PyPI, `pip install enclave-ontos` is the demo hook that
  makes vertical ontologies + sample corpora shareable outside the
  repo.
- **Observability follow-up.** Prometheus emit + retention monitor
  + mkdocs site are the natural next block after 0.1.0 lands and
  we see how operators actually run it.
- **Enclave Scribe cutover.** Version-independent; a `ScribeBackend`
  release is a minor bump (0.2.0) once the adapter lands.
