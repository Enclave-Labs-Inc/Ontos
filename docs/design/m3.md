# M3 design — planner / executor split with PPR + PathRAG-style pruning

Status: **implemented (M3.a + M3.b + M3.c).** This doc captures the
load-bearing decisions after the fact.

## Goal

Split the retrieval path into a Planner (LLM-side, non-deterministic)
and an Executor (deterministic, no LLM). The Planner emits a typed
`Plan` validated against the ontology; the Executor runs the plan
against the store and ranks with Personalized PageRank + PathRAG-style
path scoring. Ships the new `ask` MCP tool that agents use as their
default retrieval entry point.

## Why split

CypherBench (ACL 2025) found that even best-in-class LLMs land at
~60% execution accuracy on Text2Cypher, and the dominant failure
modes are structural (reversed relation direction, entity linking,
schema violations). Handing the LLM the whole task in one shot
concentrates all of those failures on a single call.

The plan/execute split lets us:

- **Constrain the LLM to a typed schema** — the Planner emits a `Plan`
  that Pydantic + the ontology reject at build time. Malformed
  outputs never reach the store.
- **Run the actual traversal deterministically** — the Executor takes
  a validated Plan and produces reproducible ranked results. Same
  plan + same store = same output.
- **Keep the Scribe drop-in seam** — `LLMPlannerBackend` is a narrow
  Protocol, same shape as `ontos.extraction.LLMBackend`. Scribe
  replaces the Planner LLM without touching the Executor.

## `Plan` schema (M3.a)

```python
class Plan(BaseModel):
    seed: SeedByEntity | SeedByKeyword  # discriminated on `kind`
    steps: list[TraversalStep]           # <=8, each depth <=5
    as_of: datetime | None = None
    limit: int  # <=200
```

`Plan.build(...)` validates every referenced relation against the
declared `Ontology`, so a Planner that emits `haunts` when the
ontology declares only `knows` gets rejected at build time — not
inside the Executor, not inside Cypher.

## Executor pipeline (M3.b)

Deterministic. No LLM calls.

1. **Seed** — resolve `plan.seed` into initial entity ids. Keyword
   seeds go through `store.search()`; entity seeds are trivial.
2. **Expand** — for each `TraversalStep`, call `store.traverse()` with
   the step's relations, depth, and direction. Track min-hop-distance
   per fact from any seed.
3. **PPR** (HippoRAG-style) — build a NetworkX DiGraph from the
   fetched facts, weight edges by fact confidence, run
   `nx.pagerank(personalization={seeds: 1.0})`. Each fact's PPR score
   = `max(source_ppr, target_ppr)`.
4. **PathRAG-style flow score** — `score = (α ^ hops) * confidence`
   with a 1.25× boost when the fact directly touches a seed. Drop
   facts whose flow < θ (early-stop pruning).
5. **Combine** — `combined = ppr * path`; sort descending; truncate
   to `plan.limit`.

Parameters chosen from the primary sources:
- **PPR damping `α_ppr = 0.5`** — HippoRAG default.
- **Path decay `α = 0.8`** — middle of PathRAG's [0.6, 0.9]
  recommended range.
- **Path early-stop `θ = 0.05`** — PathRAG default.
- **Executor `_MAX_TRAVERSAL_DEPTH = 10`** — defensive cap at the
  Executor boundary even though the plan schema also caps depth.

Non-convergence in `nx.pagerank` (rare, degenerate graphs) falls back
to uniform seed weight rather than raising — the query still returns
useful ranked results.

## `ask` MCP tool (M3.c)

New tool: `ask(question, agent_identity, acting_on_behalf_of?)`.
Runs the full NL → Planner → Executor → ranked hits path.

Fail-loud posture on every branch:

- **No planner configured** — structured error + audit record. The
  operator has not wired an LLM; degrading to a raw store call would
  break the schema-strict contract silently.
- **No ontology configured** — structured error + audit. The Planner
  needs the ontology to validate.
- **Planner raises `PlannerError`** — structured error + audit record
  containing the planner id and failure reason.
- **Executor produces no hits** — that's fine, return empty; the
  audit record still captures the plan so regulators can reproduce.

Every successful `ask()` writes the **exact Plan JSON** into the
Article-12 audit record's `tool_arguments` field. This is the
compliance guarantee: a regulator reviewing an answer can reconstruct
exactly what the runtime asked for.

## What we deliberately NOT doing in M3

- **Benchmark harness** — the plan calls for LOCOMO / HotpotQA /
  CypherBench-shaped harnesses under `tests/benchmarks/`. Landing
  those together with the executor risks conflating "executor works"
  with "executor scores well." M3.d follow-up will add the harnesses
  and track them as non-gate metrics.
- **Multi-plan speculation** — the Planner emits one Plan per
  question. Beam-search or plan ensembling is a Scribe-era
  optimization.
- **Fine-tuned confidence calibrator** — path scoring uses the raw
  extraction confidence. A trained calibrator lands with Scribe.
- **Query rewriting** — the Planner sees the raw question; no
  synonym expansion or paraphrase. Deferred pending real-corpus
  benchmarks.
- **Multi-question planning** — one question in, one plan out. Chain
  reasoning over multi-turn questions is agent-loop concern, not
  Planner concern.

## Roadmap tie-ins

- **M4** streaming CDC ingestion — the `ask` audit records will start
  seeing writes from ingestion under the same `tool_invoked` shape,
  giving operators one uniform log of every read + write.
- **M3.d benchmark harness (follow-up)** — LOCOMO ingest + query
  path replayed through `ask()`; tracks recall@k, latency,
  token-per-answer. Non-gate; regression detection only.
- **Enclave Scribe cutover** — `LLMPlannerBackend` is the drop-in;
  same pattern as `ontos.extraction.LLMBackend`. Both extractors
  and both planners can run side-by-side during the switch on a
  benchmark corpus.
