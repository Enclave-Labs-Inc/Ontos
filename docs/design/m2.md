# M2 design — authz backend + persistent Article-12 audit

Status: **implemented (M2.a + M2.b + M2.c).** This doc captures the
load-bearing decisions after the fact for future readers and Scribe-era
follow-ups.

## Goal

Ship the two subsystems the M1 design deferred to M2:

1. A real authorization layer that replaces the M1
   `acl_subject == fact.acl_ref` shim with a per-tenant authz backend
   the operator can configure (OpenFGA, SpiceDB, or an in-memory dev
   stub). Traversal still prunes at query time; no node-existence
   leaks.
2. A persistent Article-12 audit sink that survives restarts and
   satisfies the EU AI Act's ≥6-month retention obligation for
   high-risk AI systems.

Neither adds a new MCP tool. The MCP surface stays exactly as M1 shipped
it; the changes are all behind `build_server()`.

## AuthzBackend architecture (M2.a)

The design rejects the "call authz per edge from Cypher" pattern —
Neo4j can't cheaply call out to Python during traversal, and even if
it could, per-edge round trips to OpenFGA would dominate query
latency at scale.

Chosen shape: **resolve once per request, filter at query time.**

- Every MCP tool that touches storage calls
  `authz.list_authorized_objects(acting_on_behalf_of, VIEW)` once at
  request start.
- The resulting `allowed_acls: list[str]` is passed into every store
  method (`search`, `traverse`, `facts_for_entity`).
- The store filters facts against the list — Neo4j via a single
  `WHERE r.acl_ref IN $allowed_acls` clause on the traversal itself,
  NetworkX via a set membership check during BFS. Both prune at query
  time; forbidden nodes never materialize.

The four-way precedence in the `_acl_allows` matrix (M2.a):

| `fact.acl_ref` | `allowed_acls` (M2) | `acl_subject` (M1 shim) | Result |
|---|---|---|---|
| `None` | any | any | ✅ public |
| set | list containing it | any | ✅ M2 authz path |
| set | list not containing it | any | ❌ M2 authz path |
| set | `None` | matches | ✅ M1 shim (dev) |
| set | `None` | mismatch or `None` | ❌ deny-by-default |

`allowed_acls` wins over `acl_subject` when both are provided — the
M1 shim exists only as a fallback for `authz=None`.

**Backends shipped:**

- `InMemoryAuthz` — dict-of-tuples, sync grant/revoke, async check/list.
  Dev + tests only.
- `OpenFGAAuthz` — thin adapter around `openfga-sdk`. Behind the
  `authz` optional extra; loaded via `from_env()` (`FGA_API_URL`,
  `FGA_STORE_ID`, `FGA_API_TOKEN`, `FGA_MODEL_ID`). Deferred import
  so the base install stays lightweight.

**Failure discipline:** `AuthzError` is reserved for the *backend*
being unreachable or misconfigured. A failed check is a deny, not an
error. `AuthzError` MUST NOT be swallowed by the request path — a
request that can't be authorized fails closed.

## PostgresAuditEmitter architecture (M2.b)

The `AuditSink` Protocol (structural) captures what both the in-memory
`AuditEmitter` and the persistent `PostgresAuditEmitter` guarantee:

- `emit(...)` returns an `AuditRecord` with all 12 Article-12 fields.
- `by_query_id(query_id)` returns the record for that call.
- `verify_chain()` re-hashes every record and checks the `prev_hash →
  hash` chain.

The persistent implementation is **async-only** — the sync methods on
the `AuditSink` shape raise a clear `RuntimeError` pointing at the
`*_async` equivalents. Silent behavior differences between backends
would be much worse than an explicit hard fail.

**Schema:**

```sql
CREATE TABLE ontos_audit_records (
    query_id   VARCHAR(64) PRIMARY KEY,
    ordinal    BIGSERIAL   NOT NULL UNIQUE,
    timestamp  TIMESTAMPTZ NOT NULL,
    article12  JSONB       NOT NULL,
    prev_hash  VARCHAR(64),
    hash       VARCHAR(64) NOT NULL
);
CREATE INDEX ix_audit_timestamp ON ontos_audit_records (timestamp);
CREATE INDEX ix_audit_ordinal   ON ontos_audit_records (ordinal);
```

`ordinal` establishes chain order and lets `verify_chain_async()` walk
the sequence deterministically. `article12` is JSONB so we can query
individual fields for compliance reporting without shredding the
schema.

**Retention:** `prune_expired(older_than: datetime)` deletes rows past
the operator's window. Pruning breaks the chain back to genesis — you
cannot delete data and preserve full-history verifiability. What we
CAN guarantee: the retained prefix is internally consistent, so
`verify_chain_async()` still returns True for what's kept. Regulators
can verify no post-retention record was tampered with.

**Idempotent init:** `initialize()` uses SQLAlchemy `create_all()`
under `IF NOT EXISTS` semantics. Safe to call on every boot.

**Driver constraint:** `from_url()` refuses non-async URLs. Must be
`postgresql+asyncpg://` (prod) or `sqlite+aiosqlite://` (dev). A sync
driver would deadlock the FastMCP request path.

## What lands in M2.c (composition test)

Five end-to-end tests through the FastMCP in-memory Client:

- **Authz wired end-to-end.** Alice grants let her see `acl:hr` facts;
  Bob (no grants) doesn't.
- **Policy decisions recorded in audit.** Every request that consults
  authz leaves a `policy_decisions` breadcrumb in the audit record —
  the compliance evidence trail.
- **No-authz path preserves M1 shim.** With `authz=None`, the M1
  `acl_subject==acl_ref` match still works. Guard against regression
  during the M2 refactor.
- **Persistent audit survives new emitter instance.** Emit via one
  `PostgresAuditEmitter`, read via a fresh instance against the same
  Postgres. Proves data actually persisted.
- **Authz and bitemporal compose.** `as_of` queries respect authz AND
  temporal validity together.

## What we're deliberately NOT doing in M2

- **OpenFGA container in CI.** M2.a defines the adapter and unit-tests
  it via `InMemoryAuthz` composition; real OpenFGA integration is
  exercised manually by the operator, per the sovereignty invariant.
  Landing an OpenFGA container in CI is a follow-up if we ever find a
  regression the Protocol conformance test can't catch.
- **Merkle-tree retention checkpoints.** Simple prune-and-preserve is
  enough for M2. If a regulator ever asks "prove nothing was deleted"
  we'll add checkpoint hashing then.
- **Multi-relation authz.** Only `VIEW` today; write / approve
  relations land when a use case forces them.
- **Cross-region audit replication.** Single-Postgres-cluster is fine
  for M2; a regulated customer with regional obligations plumbs
  their own Postgres HA and follows the normal Postgres-in-VPC
  runbook.

## Roadmap tie-ins

- **M3** planner/executor split — the planner emits policy_decisions
  the executor consults, and both feed the same audit sink; no new
  authz surface needed.
- **M4** streaming CDC ingestion — writes must still emit audit
  records; `AuditSink.emit_async` accepts arbitrary
  `tool_arguments` so we can log ingest events under a
  `tool_invoked="ingest"` synthetic tool.
