# M7 design — vertical launch package (ontologies)

Status: **M7.a (fintech ontology) + M7.b (pharma ontology) shipped in
this PR. M7.c (sample corpora), M7.d (graded questions), and M7.e
(`ontos vertical` CLI subcommand) will land in follow-up PRs.**

## Goal

Turn `pip install enclave-ontos` from "a runtime with a Person +
Company + 3 relations toy schema" into "a runtime that speaks the
vocabulary of the two verticals Enclave sells into first — financial
services and pharma / life sciences."

An ontology is the load-bearing artifact for every downstream layer:
extraction is prompted with the schema, the planner validates
generated plans against it, the executor's cardinality checks read
from it, and the graded questions in M7.d bind their expected paths
to it. So M7 starts with the ontologies alone. Corpora and questions
follow in separate PRs where the scope decisions (synthetic vs
real, EDGAR vs SEC-full-text-search, ClinicalTrials.gov snapshot
size) can be discussed in isolation.

## What ships in this PR

Two YAML files under `docs/ontology/examples/` and their regression
tests under `tests/unit/`:

- `fintech.yaml` — 15 entity types, 22 relations, 22 patterns.
  Vocabulary grounded in **SEC Form 10-K** structure (Items 1, 1A,
  7, 8; 8-K trigger events; DEF 14A governance) and **Federal
  Reserve SR 11-7** model-risk management.
- `pharma.yaml` — 16 entity types, 25 relations, 25 patterns.
  Vocabulary grounded in the **ClinicalTrials.gov** data model, the
  **FDA regulatory submission ladder** (IND → NDA/BLA →
  sNDA/sBLA/MAA), **ICH E6 R2** GCP roles, and **GxP** (GMP/GLP/GCP)
  quality-system vocabulary.

Both ontologies pass the existing loader's referential-integrity +
cardinality + reserved-name checks unchanged.

## Design decisions

### Every entity has to be extractable from a real document

The extraction-target discipline is what separates a serious ontology
from a whiteboard exercise. Every entity and relation in both files
has a specific document type it comes from:

- Fintech: real public 10-Ks (EDGAR), 8-Ks, DEF 14As, and Federal
  Reserve supervisory letters.
- Pharma: real ClinicalTrials.gov records, FDA structured product
  labels, and FDA-483 inspection observations.

Nothing speculative or "would be nice." If an LLM extractor can't
plausibly pull it from a real document in that vertical, it's not in
the ontology.

### Cross-source identifiers are first-class

Every ontology has to have a load-bearing join key on the entity
type that appears across every source in that vertical:

- Fintech: `Company.cik` (SEC Central Index Key). Every 10-K, 10-Q,
  8-K, DEF 14A, and Form 4 in EDGAR is keyed by CIK. Without it,
  entity resolution across filings falls back to fuzzy name match.
- Pharma: `ClinicalTrial.nct_id` (ClinicalTrials.gov ID) and
  `ManufacturingSite.fda_establishment_id`. Every registered trial
  and every GMP-inspected site has one; without it, the trial and
  the sponsor's IND / NDA can't be joined.

The regression tests pin these as *required* (via test assertion
rather than schema `required: true`, because the extractor may
legitimately produce a preliminary entity before the identifier is
resolved).

### Cardinality is set from real corporate / clinical reality

CypherBench's failure-mode #3 ("reversed direction / pattern
misalignment") is the largest silent-failure category for Text2Cypher
against a real ontology. Getting cardinality right at the ontology
level lets the planner reject plans that violate it before the
executor ever runs. Examples where the direction matters:

- Fintech: `Company --filed-> Filing` is `one_to_many` (one issuer
  per filing, but a company files many filings). Getting this
  backwards would let the planner emit `Filing --filed-> Company`
  which would return the wrong node type.
- Fintech: `Company --audited_by-> Auditor` is `many_to_one` because
  a public company has exactly one independent auditor of record at
  any time. `many_to_many` would let the planner return a spurious
  "companies with multiple concurrent auditors" answer.
- Pharma: `RegulatorySubmission --reviewed_by-> Regulator` is
  `many_to_one` because a submission goes to exactly one regulator's
  review division. `many_to_many` would let the planner conflate a
  US IND and an EU CTA as if they were the same submission.

The regression tests pin the load-bearing cardinalities so a
well-meaning "clean-up" can't quietly widen them.

### Provenance chains are valid multi-hop patterns

The single most-important compliance question in both verticals is a
multi-hop-with-provenance question:

- Fintech: *"Which 10-K filings in Q4 2024 disclose a supply-chain
  risk originating in Taiwan?"* — a four-hop chain:
  `Company --filed-> Filing --contains_section-> FilingSection
  --discloses_risk-> Risk` with `Risk.topic = "supply-chain"` and
  `Risk.geography = "Taiwan"` and `Filing.fiscal_quarter = 4` and
  `Filing.fiscal_year = 2024`.
- Pharma: *"Which trials evaluate this drug, run by this CRO, at
  these sites, and report these adverse events?"* — a five-hop
  chain: `Drug --evaluated_by (reverse)-> ClinicalTrial
  --conducted_by-> CRO`, plus `ClinicalTrial --enrolls_at->
  TrialSite`, plus `ClinicalTrial --reports_event-> AdverseEvent`.

Both chains are pinned as required valid patterns in the regression
tests so an edit that breaks a hop causes a test failure with a
useful error message, not silent fall-back to vector search.

### Reused entity types (Person, Company, Regulator, Regulation)
### are ontology-scoped, not shared across files

`Person`, `Company`, `Regulator`, `Regulation` appear in both files
by design. They're the same conceptual type but the property mix
differs (Company in fintech has `cik` and `ticker`; Company in
pharma has `duns` and `fda_establishment_id`). Sharing them across
files would force one file to carry properties irrelevant to it.

Loading two ontologies simultaneously is out of scope for M7 — each
ontology is loaded independently per graph instance today. When we
add multi-ontology stores (M9?), we'll add a namespace prefix
convention (`fintech:Company` vs `pharma:Company`) rather than
merging schemas.

## What M7 deliberately doesn't ship

- **Sample corpora.** Deferred to M7.c. Two open scope questions
  should be resolved before that PR opens:
  1. Synthetic hand-authored excerpts (small, no licensing question,
     easy to make demonstrably diverse) vs real EDGAR /
     ClinicalTrials.gov snapshots (bigger, real-world messiness,
     copyright is fine for both sources but git-history bloat is
     real).
  2. Corpus size — 5 documents each is enough to exercise the graded
     questions; 20 each starts to stress the store and the planner.
- **Graded questions.** Deferred to M7.d. Each question has an
  expected multi-hop path shape and expected provenance chain, so
  the test file needs to bind to a specific corpus — hence must
  come after M7.c.
- **`ontos vertical` CLI subcommand.** Deferred to M7.e. Loads the
  shipped ontology + corpus into the currently-configured store
  with one command. Depends on M7.c to have anything to load.
- **Legal / defense / gov / healthtech ontologies.** Financial
  services and pharma are the two Enclave sells into first. The
  other three verticals wait until we have design-partner input on
  which vocabularies they actually need.

## Follow-ups after M7 ships fully

- **Extraction validation.** Once the corpora land in M7.c, run the
  `LlmExtractor` against them and see how well OllamaBackend +
  OpenAIBackend can actually populate these ontologies. Any entity
  or relation with <60% extractor recall is a candidate for
  ontology-level clarification (better description text, tighter
  cardinality, or removal).
- **Ontology loading via CLI.** `ontos ontology load fintech` as
  first-class-command (short of `ontos vertical`, which does more).
- **Ontology-diff tool.** As we iterate these two ontologies from
  real design-partner feedback, `ontos ontology diff old.yaml
  new.yaml` becomes worth building.
- **LinkML export.** `docs/ontology/examples/*.linkml.yaml` versions
  of both files for teams that already invest in LinkML tooling.
  Wire up the deferred loader (`ontos/ontology/loader.py:170`) at
  the same time.

## Roadmap tie-ins

- **First actual demo.** M7 ships the vocabulary; M7.c + M7.d ship
  the corpus and graded questions that turn `pip install
  enclave-ontos` into a 60-second walkthrough for a compliance team.
- **Extraction quality benchmark.** The graded questions from M7.d
  double as the input for the benchmark harness landed in M3.d,
  giving the first real vertical numbers (recall@k, provenance
  precision) that a design partner can review.
- **Enclave Scribe cutover.** When Scribe lands as an extractor,
  the M7.a/b ontologies are what it will be evaluated against — a
  Scribe pass is a re-run of the same extractor against the same
  corpus with the same ontology, comparing recall / precision on
  the same graded questions.
