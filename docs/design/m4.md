# M4 design — resolver cascade, connectors, Helm chart

Status: **implemented (M4.a + M4.b + M4.c).** Also picks up the
**M3.d benchmark harness** that the M3 design doc deferred.

## Goal

Ship the three pieces the M0 plan named for M4:

1. **Entity-resolution cascade** so ingestion writes go through
   Rules → ML → LLM tiers before storage. Cascade harness ships now
   with the Rules tier only; ML and LLM tiers plug into the same
   Protocol.
2. **Connector interface** so per-tenant source integrations
   (Slack, Drive, Confluence, Jira, Salesforce, GitHub) can be
   added without touching the ingest pipeline.
3. **Helm chart** so regulated deploys have a first-class in-VPC
   K8s install path with deny-egress-by-default and KMS-fed
   secrets.

Bitemporal writes + `as_of` queries were named for M4 in the original
plan but already landed in M0/M1.b (NetworkxStore + Neo4jStore
implement bitemporality; `as_of` flows through every read tool).

## Entity-resolution cascade (M4.a)

Industry consensus per Round-2 research: **cheap deterministic rules
first, statistical matcher second, LLM only for the ambiguous long
tail.** Each tier's `unresolved` becomes the next tier's input; all
tiers' merges accumulate in the final `ResolutionResult`.

### `Resolver` Protocol

```python
class Resolver(Protocol):
    id: str
    version: str
    async def resolve(self, candidates: list[Entity]) -> ResolutionResult: ...
```

Result carries `entities` (canonical), `merges` (breadcrumbs), and
`unresolved` (fell through this tier). `Cascade` drains the queue
across tiers — no entity is ever dropped.

### `ExactMatchResolver` (Rules tier)

Buckets candidates by `(type, casefolded canonical_name)`, merges
collisions, preserves aliases from every merged entity. Emits one
`MergeRecord` per non-trivial merge (single-occurrence entities
pass through with no record — keeps audit sparse).

Cross-type matches never collapse (`Person("Acme")` and
`Company("Acme")` stay separate).

### `MergeRecord` — the audit contract

The M1.d design pinned this as a hard requirement: regulators
tracing an answer must be able to reconstruct every original
entity id that merged into a canonical. `MergeRecord` is frozen
Pydantic with `(canonical_id, merged_ids, resolver_id,
resolver_version, resolved_at, reason)`. The
`test_merge_lineage_recoverable_from_merge_records` test pins that
lineage can be rebuilt from a stream of records.

### What lands later

- **ML tier** — Splink / Zingg-shaped statistical matcher for the
  1M–100M-record scale range. Plugs into `CascadeResolver` via the
  same Protocol.
- **LLM tier** — for the ambiguous long tail. Reuses the
  `LLMBackend` seam from M1.d / M3.a.
- **Wire the cascade into the ingest pipeline** — currently M4.a
  ships the cascade standalone; hooking it into the extractor path
  lands with the connector integration when ingest goes end-to-end.

## Connector interface (M4.b)

```python
class Connector(Protocol):
    id: str
    source_kind: str
    def iter_documents(self) -> AsyncIterator[SourceDocument]: ...
```

`SourceDocument` carries `source_id` (stable across re-ingests),
`text`, `metadata`, `acl_ref`. Connectors NEVER touch the ontos
store directly — the ingest pipeline consumes their stream, hands
each document to the extractor (M1.d), resolves entities via the
cascade (M4.a), then writes to the store. Keeping connectors
state-free means per-tenant vendoring or replacement without
touching pipeline code.

### Shipped

- **`TextConnector`** — dev/test connector that yields a fixed
  dict of documents. Every real-world connector reduces to
  "iterate documents from a source"; this lets end-to-end tests
  drive ingest without a real service.
- **`SlackConnector` (placeholder)** — satisfies the Protocol
  structurally so plumbing typed on `Connector` compiles.
  `from_token()` and `iter_documents()` raise loud (real Slack
  takes a per-tenant bot token which is out of scope for a
  runtime library; the impl lands with the per-tenant onboarding
  work).

### What lands later

- Real `SlackConnector` (slack-sdk).
- `DriveConnector` (google-api-python-client) — mime-type
  filtering + folder scoping.
- `ConfluenceConnector` (atlassian-python-api).
- `JiraConnector`, `GitHubConnector`.
- **CDC pipeline** — connectors today are pull-based
  (`iter_documents` walks history once); streaming CDC via
  webhooks / event subscriptions is a post-M4 concern.

## Helm chart (M4.c)

`deploy/helm/ontos/` — the regulated-deploy install path.

### The three sovereignty defaults

1. **Deny-egress NetworkPolicy.** The pod cannot phone home.
   Explicit whitelist under `networkPolicy.allowedEgress` covers
   only the storage backends the runtime supports (Neo4j,
   Postgres, OpenFGA) plus kube-dns. Everything else is dropped
   at the CNI.
2. **KMS-fed Secrets.** The chart NEVER accepts key material
   inline. `ONTOS_AUDIT_SIGNING_KEY`, `NEO4J_PASSWORD`,
   `ONTOS_AUDIT_DB_URL`, `FGA_API_TOKEN` all resolve from
   `Secret` refs you populate externally via
   external-secrets-operator sourced from your KMS / Vault /
   customer key manager.
3. **Read-only root filesystem + non-root UID 1000.** Writes go
   only to explicitly-mounted `emptyDir`s (`/tmp`,
   `/var/lib/ontos/audit-logs`). Matches the Dockerfile.

### CI gate

Two new steps in `.github/workflows/ci.yml` run on every PR:

- `helm lint deploy/helm/ontos` — chart syntax.
- `helm template ... > /dev/null` — every template renders into
  valid YAML.

A broken chart fails CI. This closes the "chart drifts silently
until someone tries to install it" loop.

### What's deliberately NOT in the chart

- Neo4j, Postgres, OpenFGA themselves — bring your own; each is
  the customer's operator + storage story.
- Ingress — every regulated deploy fronts the MCP endpoint with
  its own gateway (Envoy / Istio / Traefik with their mTLS +
  logging stack).

Each is intentionally the customer's decision. The chart deploys
only the Ontos runtime and its explicit egress rules.

## Benchmark harness (M3.d)

`tests/benchmarks/harness.py` — reusable harness that takes a graded
question set + a callable and reports recall@k, precision, latency
percentiles. **Non-gate**: LLM-driven quality drifts on model
updates, and gating on drift either freezes the stack or produces
noisy CI. What CI does catch: crashes, empty results on questions
that used to have hits, >2× latency spikes (the assertions in
`test_synthetic`).

New pytest marker `benchmark`; `addopts` excludes both `integration`
and `benchmark` by default. Real benchmarks against LOCOMO /
HotpotQA / CypherBench land as follow-ups when we have a real LLM
planner + licensed corpora.

## Roadmap tie-ins

- **Ingest end-to-end wiring** — M4.b ships the connector interface
  and M4.a ships the resolver cascade; the pipeline that stitches
  them together (Connector → LlmExtractor → CascadeResolver → Store)
  is small enough to land as an M4 follow-up PR when it becomes
  useful (i.e. when we have a real corpus to test against).
- **Real connectors (Slack / Drive / Confluence)** — per-tenant
  onboarding work; lands when a design partner names a corpus.
- **Real ML tier for ER** — Splink integration when we have >1M
  records to dedupe.
- **Enclave Scribe cutover** — unchanged shape; drop-in through
  `LLMBackend` (extractor) and `LLMPlannerBackend` (planner). ER
  cascade already accepts an LLM tier; that plugs in the same way.
